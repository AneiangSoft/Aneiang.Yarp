# Aneiang.Yarp Dashboard 前端重新设计方案

> **目标用户**：运维人员、初级开发人员
> **设计原则**：上手快、操作便捷、全量多语言、企业管理风格
> **现状**：20 个页面、49 个 JS 文件、20 个 i18n JSON 文件，导航分 8 组过于零散

---

## 一、导航架构重组

### 现状问题
- 8 个导航组（仪表盘/网关管理/插件/监控运维/安全防护/流量优化/审计/系统管理）过于碎片化
- 插件配置页面（限流/WAF/重试/缓存/服务发现）与"插件管理"割裂，用户不知道它们的关系
- "监控运维"下 5 个入口太多，且"流量监控"和"流量指标"容易混淆
- 没有面包屑，深层页面容易迷失

### 新导航（4 组 + 全局搜索）

```
┌─────────────────────────────────────┐
│  网关维护仪表盘          [搜索] [中/EN] [退出] │
├─────────────────────────────────────┤
│                                     │
│  📊 总览                             │
│     · 仪表盘                         │
│                                     │
│  🌐 网关配置                         │
│     · 服务集群                       │
│     · 路由配置                        │
│                                     │
│  🧩 插件中心                         │
│     · 插件管理（全局开关+状态）        │
│     · 插件资源（资源监控）             │
│     · 策略配置（合并以下5个页面）      │
│       ├ 限流策略                      │
│       ├ WAF 防火墙                    │
│       ├ 请求重试                      │
│       ├ 响应缓存                      │
│       └ 服务发现                      │
│                                     │
│  📈 运维监控                         │
│     · 实时日志                       │
│     · 熔断状态                       │
│     · 流量监控（合并 traffic + metrics）│
│     · 集群指标                       │
│     · 审计日志                       │
│                                     │
│  ⚙️ 系统管理                         │
│     · 系统设置                       │
│     · 配置历史                       │
│                                     │
└─────────────────────────────────────┘
```

### 关键变化
| 变化 | 说明 |
|---|---|
| 8 组 → 6 组 | "安全防护"和"流量优化"合并进"插件中心 > 策略配置" |
| 插件页面归一 | 5 个插件配置页面作为"策略配置"的子页面，共享统一的绑定管理 UI |
| 流量页面合并 | "流量监控"和"流量指标"合并为一个页面，用 Tab 切换视图 |
| 面包屑 | 每个页面顶部增加面包屑导航（首页 > 网关配置 > 服务集群） |
| 全局搜索 | 顶栏增加搜索框，可快速跳转到任意页面或搜索路由/集群 |

### 2.6 插件中心 - 策略配置页（合并 5 个页面）

**现状问题**：RateLimit / Waf / Retry / ResponseCache / ServiceDiscovery 各自独立页面，结构和功能几乎一样，但用户需要在 5 个页面间切换

**重新设计**：合并为 1 个"策略配置"页面，左侧选择插件，右侧管理绑定

```
│  首页 > 插件中心 > 策略配置                       │

│   WAF  ● │     生效。支持固定窗口、滑动窗口、令牌桶│
│   重试 ○ │                                      │
│   缓存 ○ │  ┌──┬──────────┬──────────┬────┬────┐│
│   发现 ● │  │  │作用域     │配置摘要   │状态│操作││
│          │  │ 1│路由 api-* │100 req/s │启用│✏🔄🗑││
│          │  │ 2│集群 web   │500 req/s │停用│✏🔄🗑││
│          │  └──┴──────────┴──────────┴────┴────┘│
│          │                                      │
└──────────┴──────────────────────────────────────┘
```

**改进点**：
- 左侧插件列表带状态指示（● 启用 / ○ 停用）
- 右侧动态加载选中插件的绑定管理 UI
- 复用 `plugin-binding-manager.js` 逻辑

## 三、统一交互模式

### 3.1 帮助说明条
每个页面顶部统一增加可折叠的帮助说明：
```html
<div class="page-help-bar">
  <i class="bi bi-info-circle"></i>
  <span data-i18n="page.help.clusters">服务集群是一组后端服务节点的集合...</span>
  <button class="btn-close-help">×</button>
</div>
```

### 3.2 空状态统一
所有列表页空状态统一为：图标 + 说明 + 引导按钮
```html
<div class="empty-state">
```

### 7.2 请求调试器（Debug Console）— 研发最核心需求

**痛点**：研发调试时不知道请求是否经过网关、怎么匹配的路由、哪个插件拦截了

**设计**：在总览页或路由页增加"请求调试"入口
```
┌─────────────────────────────────────────────────┐
│  请求调试器                                       │
├─────────────────────────────────────────────────┤
│  方法: [GET ▼]  URL: [/api/users/123    ] [发送] │
│  Headers: [Authorization: Bearer xxx   ] [+]    │
│  Body:    [{ "name": "test" }          ]         │
├─────────────────────────────────────────────────┤
│  📋 请求链路追踪                                  │
│  ┌─────────────────────────────────────────────┐│
│  │ ① 路由匹配  matched: api-users  (2ms)       ││
│  │ ② WAF 检查   passed  (1ms)                  ││
│  │ ③ 限流检查   passed  42/100 req/s  (0ms)    ││
│  │ ④ 转发请求   cluster-a → 10.0.1.2:8080     ││
│  │ ⑤ 响应返回   200 OK  (15ms)                 ││
│  │ ⑥ 日志记录   written  (1ms)                 ││
│  └─────────────────────────────────────────────┘│
│                                                 │
│  📤 响应                                         │
│  Status: 200 OK  (总耗时: 19ms)                 │
│  Headers: Content-Type: application/json        │
│  Body: { "id": 123, "name": "test" }           │
└─────────────────────────────────────────────────┘
```

**价值**：
- 研发排查"为什么我的请求 502"时，一眼看到是哪一步出了问题
- 每个插件显示耗时，性能瓶颈一目了然
- 不需要 curl/Postman，直接在仪表盘内完成调试

## 十、菜单栏重新设计

### 10.1 当前菜单问题分析

#### 结构现状
```
8 个分组，17 个菜单项（平均每组仅 2 项）
├── 仪表盘 (1 项)
├── 网关管理 (2 项)
├── 插件 (2 项)
├── 监控运维 (5 项)
├── 安全防护 (2 项)     ← WAF、限流其实是插件
├── 流量优化 (3 项)     ← 重试、缓存、服务发现也是插件
├── 审计 (1 项)
└── 系统管理 (2 项)
```

#### 7 个核心问题

| # | 问题 | 影响 |
|---|---|---|
| 1 | **分组过多** | 8 组 17 项，每组平均 2 项，侧边栏拉很长 |
| 2 | **插件被割裂** | WAF 和限流在"安全防护"，重试/缓存/服务发现在"流量优化"，但它们都是插件，应该归到"插件中心" |
| 3 | **流量监控 vs 流量指标** | 两个菜单项名字几乎一样，用户分不清区别 |
| 4 | **无状态指示** | 菜单项没有健康/告警徽章，用户要点进去才知道状态 |
| 5 | **无折叠到图标模式** | 不能收起为图标条节省屏幕空间 |
| 6 | **i18n 硬编码** | 标题用 `isEn ? "..." : "..."` 而非 `data-i18n` |
| 7 | **无快捷入口** | 侧边栏只能导航，不能快捷操作（如新建集群） |

### 10.3 徽章/状态指示器设计

每个菜单项右侧可显示实时状态徽章：

```
· 服务集群                     12        ← 灰色计数
· 路由配置                     48        ← 灰色计数
· 插件管理                     8/10      ← 绿色/灰色 启用/总数
· 实时日志                     ●         ← 绿色=已连接 灰色=断开
· 熔断状态                     ⚠ 1      ← 红色告警数
· 流量监控                     42 req/s ← 实时QPS（灰色小字）
```

#### 徽章类型

| 类型 | 样式 | 数据来源 | 示例 |
|---|---|---|---|
| 计数 | 灰色圆角 | 列表总数 | `12`、`48` |
| 启用比 | 绿色/灰色 | 启用/总数 | `8/10` |
| 健康点 | 绿/黄/红圆点 | 健康状态 | `●`、`⚠` |
| 实时指标 | 灰色小字 | SignalR 推送 | `42 req/s` |
| 告警数 | 红色圆角 | 异常计数 | `1` |

**实现方式**：菜单项增加 `data-badge-type` 和 `data-badge-source` 属性，JS 定时刷新。无数据时徽章隐藏。

### 10.8 交互细节

**1. 分组折叠记忆**：
- 用户折叠/展开的分组状态存入 `localStorage`
- 刷新页面后恢复，不需要每次重新展开

**2. 当前页定位**：
- 当前页所在分组自动展开
- 当前页菜单项高亮
- 如果当前页是子菜单项（如 WAF），父菜单"策略配置"自动展开

**3. 悬浮预览**（图标模式）：
- 鼠标悬浮在分组图标上 200ms 后弹出完整子菜单气泡
- 气泡内可点击导航

**4. 徽章刷新频率**：
- 计数徽章：进入页面时刷新一次
- 健康徽章：SignalR 推送更新
- 实时指标：30 秒轮询

**5. 键盘可达性**：
- `Tab` 键可以遍历所有菜单项
- `Enter` 激活
- `↑↓` 在同组内移动
